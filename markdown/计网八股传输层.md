# 第一章：传输层核心考点全覆盖

## 1. TCP 三次握手 (核心中的核心)

**① 过程详解**

* **第一次握手**：客户端发送 `SYN` 报文（Seq=x），进入 `SYN_SENT` 状态。
* **第二次握手**：服务端收到后，发送 `SYN+ACK` 报文（Seq=y, Ack=x+1），进入 `SYN_RCVD` 状态。
* **第三次握手**：客户端收到后，发送 `ACK` 报文（Ack=y+1），进入 `ESTABLISHED` 状态。服务端收到后也进入该状态。

**② 深度追问**

* **为什么三次？** 核心是为了**防止旧的重复连接初始化导致混乱**（RFC 793 核心理由）。同时也为了同步双方的序列号并确认收发能力。
* **ISN 为什么随机？** 初始序列号（ISN）随时间变动，防止被攻击者猜到序列号从而进行数据注入攻击。
* **半连接队列与全连接队列**：
* **半连接队列 (SYN Queue)**：存放收到 SYN 但未完成三次握手的连接。
* **全连接队列 (Accept Queue)**：存放已完成三次握手但未被应用层 `accept` 的连接。

## 2. TCP 四次挥手 (高频)

**① 过程详解**

1. **FIN_WAIT_1**：客户端发送 `FIN`。
2. **CLOSE_WAIT**：服务端回 `ACK`。此时服务端还可以继续发未完成的数据。
3. **LAST_ACK**：服务端发完数据，发送 `FIN`。
4. **TIME_WAIT**：客户端回 `ACK`。等待 **2MSL** 后关闭。

**② 深度追问**

* **为什么需要 TIME_WAIT？**
* **可靠地关闭连接**：防止最后一个 ACK 丢失导致服务端无法正常关闭。
* **使旧数据消失**：防止本次连接的"迷途报文"干扰下一个相同四元组的新连接。

* **为什么是 2MSL？** （最长报文段寿命）是一个报文在网络中存在的最长时间。2MSL 刚好够一个报文"走一个来回"。

* **⭐ 重要区分：四次挥手 vs 三次握手**
* **三次握手**：用于**建立连接**（SYN → SYN+ACK → ACK）
* **四次挥手**：用于**断开连接**（FIN → ACK → FIN → ACK）
* **为什么断开需要四次？** TCP是全双工通信，双方需要独立关闭各自的发送通道

## 3. TCP 重传、流量控制与拥塞控制 (高频)

**① 重传机制**

* **超时重传**：基于计时器，超过  时间未收到 ACK 则重发。
* **快速重传**：收到 3 个相同的 ACK 立即重传。
* **SACK (选择性确认)**：在 TCP 头部加入 SACK 字段，告知发送方具体哪些片段丢了，避免重传已收到的数据。

**② 流量控制 (Flow Control)**

* **滑动窗口**：接收方通过 TCP 头部的 `Window` 字段告知发送方自己还能接收多少数据（接收窗口 ）。

**③ 拥塞控制 (Congestion Control)**

1. **慢启动**： 从 1 开始指数增长。
2. **拥塞避免**： 后，改为加法增大（线性增长）。
3. **拥塞发生**：丢包时， 设为当前 ， 重置为 1（针对超时重传）。
4. **快恢复**：如果是触发了快速重传， 不回 1，而是减半后直接进入拥塞避免。

## 4. TCP vs UDP (高频)

| 特性 | TCP | UDP |
| --- | --- | --- |
| **连接性** | 面向连接 | 无连接 |
| **可靠性** | 可靠传输（重传、排序） | 不可靠（尽力而为） |
| **传输形式** | 字节流（无边界） | 数据报（有边界） |
| **首部开销** | 20-60 字节 | 8 字节 |
| **应用场景** | 文件传输、浏览器 (HTTP) | 视频会议、直播、游戏 |

## 5. TCP 报文头部字段 (中频)

* **端口号**：源端口、目的端口。
* **序列号 (Seq)**：本报文段数据的第一个字节的序号。
* **确认号 (Ack)**：期望收到对方下一个字节的序号。
* **控制位**：`SYN` (同步), `ACK` (确认), `FIN` (结束), `RST` (重置), `PSH` (推送), `URG` (紧急)。
* **窗口大小**：用于流量控制。

## 6. 其他重要考点 (低频与冷门标记)

* **TCP 粘包/拆包 (中频)**：
* **原因**：TCP 是面向字节流的，应用层协议没有定义边界。
* **解决**：固定包长度、增加特殊分隔符、在包头增加长度字段。


* **`▽` Nagle 算法与延迟确认**：
* Nagle 算法试图合并小包以提高效率，但在延迟敏感（如 SSH）场景下会造成卡顿，通常通过 `TCP_NODELAY` 禁用。


* **`▽` Keep-Alive 与心跳包**：
* TCP 自带 Keep-Alive 机制，但检测周期太长（默认 2 小时），通常在应用层自己实现心跳。


* **`▽` TCP Fast Open (TFO)**：
* 在握手阶段就携带数据，减少往返时间（RTT）。


* **`▽▽` 糊涂窗口综合症 (Silly Window Syndrome)**：
* 当接收方消费慢，每次只释放极小的窗口，导致发送方只发几个字节的有效载荷（头部开销比太大）。


* **`▽▽` 自计时与自时钟 (Self-clocking)**：
* TCP 通过 ACK 的返回频率来驱动数据的发送。


* **`▽▽` 针对 TIME_WAIT 的优化**：
* `tcp_tw_reuse`（重用端口）与 `tcp_tw_recycle`（已在 Linux 4.12 移除，因在 NAT 环境下有风险）。

## 7. 传输层常见面试追问总结

* **问：如何实现一个可靠的 UDP？**
* 答：在应用层模仿 TCP 的机制：引入序列号、ACK 确认、超时重传、滑动窗口。典型参考：QUIC 协议。


* **问：如果服务器负载过高导致全连接队列满了会发生什么？**
* 答：默认情况下服务端会丢弃后续的 ACK，客户端会重传，直到超时。或者通过配置发送 RST。


* **问：RST 包在什么情况下会出现？**
* 答：端口未监听、连接超时、强制关闭连接、或者收到不属于当前连接状态的数据包。
